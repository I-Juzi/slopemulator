# Card st-00: StServers RE — shared framework

## Goal
Write chapter `Docs/Platform/StServers/RE/00-framework.md` of the full reverse-engineering reference for the StServers (NP platform) programs. All 49 services link the same framework. This chapter describes the framework once, so that later slices (`st-01` and up) look only at service code. The reference replaces IDA for the port. Be complete and exact: addresses, enums, field layouts, timers, log strings.

## Context
- Existing specs (link to them, do not repeat them; fill only their gaps): `Docs/Platform/Sts/01-transport.md`, `02-messages.md`, `10-stservers-original.md`, `Docs/Platform/StServers/11-cligate-protocol.md` to `15-authsrv.md`, `procs.tsv`, `errcodes.tsv`. Run `python3 tools/spec_index.py <doc>` and read only the sections that you need.
- `Docs/Platform/StServers/RE/framework-funcs.tsv` lists the fingerprint (hash) of every framework function. The supervisor made it with `tools/fn_fingerprint.py`: a function is framework code when it is in HelloSrv or in at least half of the 51 binaries. The hash masks addresses but keeps the text of referenced strings and the names of imports. So two functions that differ only in a string get different hashes. The `sample_name` column has names from earlier slices, where they exist.
- `Docs/Platform/StServers/RE/service-sizes.tsv` gives the number of service-only functions per binary.

## Work (5 topics)
1. **Process start and host:** entry point, command line, service and console mode, config files (`StServer.ini` and the per-service files: every key, default and use), logging (files, levels, format), crash handling, shutdown.
2. **Service model:** the base classes and their vtables, how a service registers its commands and handlers, worker threads, the timer system, the per-connection state. This is the most important topic. See "Service recipe" below.
3. **Messages and routing:** message parse and build, the route client, the reply and error paths. Check against `Sts/01`, `Sts/02` and `14-route-client.md`. Write only what is new or different.
4. **DB call layer:** how a service calls DbSrv (proc request build, reply parse, timeouts, retries), and any local cache. Check against `12-dbsrv-contract.md`.
5. **Other shared parts:** admin HTTP pages, TLS setup (no keys: write `keyhere`), HTTP client, JSON and XML helpers, crypto helpers, counters and monitoring.

## Service recipe (the main use of this chapter)
Later slices must find a service's own parts without reading framework code. Write a section "Service recipe" with tested IDA Python snippets (8 to 20 lines each) that list, for any service binary:
- the command table: command name or id → handler address;
- the DB procs that the service calls (name, call site);
- the config keys that the service reads;
- the timers that the service starts (period in ms, callback).
Test each snippet on HelloSrv and on AuthSrv. Give the output counts for both.

## Detail level
- Cover every framework part that a service can reach. Use the fingerprint table: list the framework functions with names or strings, then work through them by topic.
- For each state machine: every state, event, transition, timer value in ms and log string.
- Long lists go in `.tsv` files next to the chapter, with a header row and an address column.
- Write a name list `Docs/Platform/StServers/RE/framework-names.tsv` (hash, HelloSrv address, name, one-line role) for every framework function that you name. Use the hash from the fingerprint table. Later slices import these names.
- If you run out of turns, write what is left in the handoff "Not done" list with addresses.
